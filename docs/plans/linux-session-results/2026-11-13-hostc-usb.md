# L4 on HOSTC — USB

L4 was "not run" on 11.11.2026 because the bricks were not cabled to HOSTC. On 13.11.2026 the
owner connected AAA, BBB and CCC to HOSTC over USB at once. Same host as the first session
(`2026-11-11-hostc.md`): Raspberry Pi 5, arm64, Debian 13, now kernel 6.18.60+rpt-rpi-2712, Node
v20.19.2; code at `edfc0b0`.

## Before the udev rule

| Check | Result |
|---|---|
| `lsusb` | three × `0694:0005 Lego Group Mindstorms EV3` |
| Kernel drivers on the bricks' interfaces | `usbhid` on all three; `usb-storage` as well on two (the bricks with an SD card) |
| `/dev/hidraw2..4` | `HID_NAME=LEGO Group CCC / AAA / BBB`, mode `crw------- root root` |
| `/dev/bus/usb/…` | `crw-rw-r-- root root` (readable, not writable) |
| `hardware-matrix.js --quick` | discovery finds AAA, CCC, BBB by name; every connect fails: `libusb: No EV3 on the USB bus reports serial <MAC>.. HID: cannot open device with path /dev/hidraw3` |

The libusb half of that message is misleading: the serial is there, the user just may not open
the device to read it. A user without the rule sees the bricks listed and cannot connect, with
no hint that permissions are the cause.

## The udev rule

Installed by the owner from a terminal (`sudo` needs a TTY; it could not be run from the Claude
session): exactly the runbook's two lines in `/etc/udev/rules.d/70-lego-ev3.rules`, then
`udevadm control --reload` and `udevadm trigger --subsystem-match=usb --subsystem-match=hidraw
--action=change`; bricks re-plugged. Afterwards each brick's hidraw node is `crw-rw----+` with an
ACL `user:<seat user>:rw-` (`uaccess`).

## Which USB backend ran

Rule: record libusb or node-hid, and every `LIBUSB_ERROR_BUSY` / `LIBUSB_ERROR_ACCESS`.

**node-hid, on all three bricks; libusb fails with `LIBUSB_ERROR_BUSY`.**

- The matrix connects with "64 B packets" (the HID path).
- The cockpit's own log, in the dev host:

  ```
  [info] USB transport registered — node-hid OK, 3 EV3 device(s) visible
  [info] USB transport — libusb available, full 1024-byte frames
  [warning] Could not read the name of AAA [<MAC>] USB without connecting; showing the USB descriptor's until it connects: Could not claim USB interface 0 on the brick. (LIBUSB_ERROR_BUSY)
  [warning] <MAC> USB: libusb unavailable (Could not claim USB interface 0 on the brick. (LIBUSB_ERROR_BUSY)). Fell back to HID, which delivers 64 bytes per packet — transfers run about forty times slower and copy/move cannot be sent at all.
  ```

- A direct probe with the `usb` module on each brick: `open()` works, interface 0 reports
  `isKernelDriverActive() = true`, `claim()` → `LIBUSB_ERROR_BUSY`. No `LIBUSB_ERROR_ACCESS` with
  the rule in place.
- The same probe on one brick with `detachKernelDriver()` first, **as the normal user**: detach
  works, `claim()` works, the endpoints read `in:1024, out:1024`; `release()` and
  `attachKernelDriver()` work and the brick's hidraw node comes back. So the libusb path can work
  on Linux once the cockpit detaches `usbhid` (or sets libusb's auto-detach); it does neither today.

## Verdict

**L4: fails** against the runbook's rule as written — the bricks are discovered by name, connect,
answer `info`, and the filesystem and telemetry checks pass over USB, three bricks at once, and
VS Code connects and lists files; but the run is on HID, not libusb, and the 99-byte check fails
on every brick because of it. **4.6.16's question — does the libusb path work on Linux — is
answered: not today (`LIBUSB_ERROR_BUSY`, `usbhid` holds the interface), and yes once the
interface is detached from `usbhid`, which works without root.**

Not run: pulling a cable during a file transfer (L4's optional second half of 4.6.16).

## Findings

1. **`LIBUSB_ERROR_BUSY` on Linux, silent fall back to HID.** The kernel's `usbhid` binds the
   brick's interface 0; the cockpit claims without detaching, so every Linux user gets the HID
   path, 64-byte packets and no copy/move. Detaching as the normal user works and yields 1024-byte
   endpoints.
2. **The activation line claims libusb works.** "USB transport — libusb available, full 1024-byte
   frames" is logged on Linux while every claim fails; it reports that the module loaded, not that
   a brick can be claimed.
3. **Without the udev rule the error hides the cause.** The bricks are listed by name and the
   connect fails with "No EV3 on the USB bus reports serial …" and "cannot open device with path
   /dev/hidraw3"; nothing says "permission" or points to the rule a user has to install.
4. **Users on Linux must install a udev rule once.** The extension cannot write `/etc/udev` and a
   `sudo` from inside it would need a terminal. The rule the runbook proposes works: `uaccess`
   gives the seat user read and write on both the USB and hidraw nodes.
5. **One 5 s timeout on BBB** in three full runs (battery read, first full run); not reproduced.
