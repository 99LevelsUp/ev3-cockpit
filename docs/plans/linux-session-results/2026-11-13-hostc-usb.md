# L4 on HOSTC — USB

L4 was "not run" on 11.11.2026 because the bricks were not cabled to HOSTC. On 13.11.2026 the
owner connected AAA, BBB and CCC to HOSTC over USB at once. Same host as the first session
(`2026-11-11-hostc.md`): Raspberry Pi 5, arm64, Debian 13, now kernel 6.18.60+rpt-rpi-2712, Node
v20.19.2; code at `edfc0b0`.

## Before the udev rule

| Check | Result |
|---|---|
| `lsusb` | three × `0694:0005 Lego Group Mindstorms EV3` |
| Kernel drivers on the bricks' interfaces | `usbhid` on all three; `usb-storage` as well on two (the bricks with an SD card) |
| `/dev/hidraw2..4` | `HID_NAME=LEGO Group CCC / AAA / BBB`, mode `crw------- root root` |
| `/dev/bus/usb/…` | `crw-rw-r-- root root` (readable, not writable) |
| `hardware-matrix.js --quick` | discovery finds AAA, CCC, BBB by name; every connect fails: `libusb: No EV3 on the USB bus reports serial <MAC>.. HID: cannot open device with path /dev/hidraw3` |

The libusb half of that message is misleading: the serial is there, the user just may not open
the device to read it. A user without the rule sees the bricks listed and cannot connect, with
no hint that permissions are the cause.

## The udev rule

Installed by the owner from a terminal (`sudo` needs a TTY; it could not be run from the Claude
session): exactly the runbook's two lines in `/etc/udev/rules.d/70-lego-ev3.rules`, then
`udevadm control --reload` and `udevadm trigger --subsystem-match=usb --subsystem-match=hidraw
--action=change`; bricks re-plugged. Afterwards each brick's hidraw node is `crw-rw----+` with an
ACL `user:<seat user>:rw-` (`uaccess`).

## Which USB backend ran

Rule: record libusb or node-hid, and every `LIBUSB_ERROR_BUSY` / `LIBUSB_ERROR_ACCESS`.

**node-hid, on all three bricks; libusb fails with `LIBUSB_ERROR_BUSY`.**

- The matrix connects with "64 B packets" (the HID path).
- The cockpit's own log, in the dev host:

  ```
  [info] USB transport registered — node-hid OK, 3 EV3 device(s) visible
  [info] USB transport — libusb available, full 1024-byte frames
  [warning] Could not read the name of AAA [<MAC>] USB without connecting; showing the USB descriptor's until it connects: Could not claim USB interface 0 on the brick. (LIBUSB_ERROR_BUSY)
  [warning] <MAC> USB: libusb unavailable (Could not claim USB interface 0 on the brick. (LIBUSB_ERROR_BUSY)). Fell back to HID, which delivers 64 bytes per packet — transfers run about forty times slower and copy/move cannot be sent at all.
  ```

- A direct probe with the `usb` module on each brick: `open()` works, interface 0 reports
  `isKernelDriverActive() = true`, `claim()` → `LIBUSB_ERROR_BUSY`. No `LIBUSB_ERROR_ACCESS` with
  the rule in place.
- The same probe on one brick with `detachKernelDriver()` first, **as the normal user**: detach
  works, `claim()` works, the endpoints read `in:1024, out:1024`; `release()` and
  `attachKernelDriver()` work and the brick's hidraw node comes back. So the libusb path can work
  on Linux once the cockpit detaches `usbhid` (or sets libusb's auto-detach); it does neither today.

## Verdict

**L4 on `edfc0b0`: fails** against the runbook's rule as written — the bricks are discovered by name, connect,
answer `info`, and the filesystem and telemetry checks pass over USB, three bricks at once, and
VS Code connects and lists files; but the run is on HID, not libusb, and the 99-byte check fails
on every brick because of it. **4.6.16's question — does the libusb path work on Linux — is
answered: not today (`LIBUSB_ERROR_BUSY`, `usbhid` holds the interface), and yes once the
interface is detached from `usbhid`, which works without root.**

The cable pull is in "After the fix" below.

## Findings

1. **`LIBUSB_ERROR_BUSY` on Linux, silent fall back to HID.** The kernel's `usbhid` binds the
   brick's interface 0; the cockpit claims without detaching, so every Linux user gets the HID
   path, 64-byte packets and no copy/move. Detaching as the normal user works and yields 1024-byte
   endpoints.
2. **The activation line claims libusb works.** "USB transport — libusb available, full 1024-byte
   frames" is logged on Linux while every claim fails; it reports that the module loaded, not that
   a brick can be claimed.
3. **Without the udev rule the error hides the cause.** The bricks are listed by name and the
   connect fails with "No EV3 on the USB bus reports serial …" and "cannot open device with path
   /dev/hidraw3"; nothing says "permission" or points to the rule a user has to install.
4. **Users on Linux must install a udev rule once.** The extension cannot write `/etc/udev` and a
   `sudo` from inside it would need a terminal. The rule the runbook proposes works: `uaccess`
   gives the seat user read and write on both the USB and hidraw nodes.
5. **One 5 s timeout on BBB** in three full runs (battery read, first full run); not reproduced.
6. **After the fix: L4 holds** — libusb on all three bricks, matrix 43/44 (TCP only), recovery
   after a cable pull. See "After the fix".

## After the fix (`linux-backend`: 2dacf24, 36818a2, 88aa096)

The owner decided (via the Windows session) that HOSTC fixes Linux USB, since it has the bricks on
the cable. What changed, Linux only (Windows untouched, pinned by tests):

1. libusb auto-detach before the claim (a hand `detachKernelDriver` + `attachKernelDriver` where
   the build has no auto-detach), then **clear-halt on both endpoints**. Without the clear-halt the
   first exchange after every detach timed out and the second worked (data toggle out of step;
   probe: `clearHalt` on either endpoint fixed 3 of 3 rounds).
2. USB discovery keeps listing a brick this provider holds. The detach takes the brick's hidraw node
   with it, and node-hid stopped listing a connected brick ("while AAA held: CCC, BBB").
3. A device the user may not open fails with `DevicePermissionError` (a `ConnectionError`, so
   nothing that counts connection failures changes), whose message names the udev rule the
   extension now ships: `native/linux/70-lego-ev3.rules`.
4. While a known message counter is awaited, an unreadable reply is stepped over like a stale one
   (bounded by the existing `MAX_STALE_REPLIES`). After a fresh plug the brick had one packet of
   garbage waiting on its IN endpoint (read before anything was sent: 1024 B at once, declared
   length 0, junk up to byte 512); the first exchange failed with "shorter than the packet it
   declares" on two of two re-plugs, and works after the fix.
5. On Linux, discovery also lists the bricks libusb enumerates. An extension host that dies holding
   a brick never gives `usbhid` back: the brick stays on the bus with no driver and no hidraw node,
   and node-hid stopped listing it. `npm run test:host` reproduces it on HOSTC every time (the test
   runner ends VS Code while activation probes the bricks' names): afterwards one brick has no
   driver on interface 0. Such a brick is now discovered and connects over libusb (20/20 `info`
   with the other two), and the libusb release gives it `usbhid` back.

Every change went test first (red, then green) and was checked by mutation: each mutation
(no platform gate, no reattach, no clear-halt, IN only, held brick not listed, no dedupe, name
lost, permission on Windows, permission lost in the provider, tolerance everywhere / without a
counter / never / unbounded) failed at least one test.

### Cable pulled during a file transfer (second half of 4.6.16)

AAA, libusb, a 4 MB upload; the owner pulled the cable at about 80 % of the first file.

```
round 1 FAILED after 10626 ms: TransportError: USB receive failed: LIBUSB_TRANSFER_ERROR
info after failure: TransportError: USB send failed: LIBUSB_TRANSFER_ERROR (3 ms)
disconnect resolved in 4 ms
discovery after: CCC, BBB
```

The loss is reported at once as a `TransportError` (which the heartbeat counts as link loss), the
next command fails in 3 ms, the disconnect resolves in 4 ms, and discovery drops the brick. Nothing
hangs. After the cable went back in: discovery lists AAA, connect over libusb (1024 B), `info`
answers, the partial file (3 760 819 B) is listed and removed.

**Verdict: holds** — recovery on libusb works on Linux.

### Space held by an interrupted upload (hypothesis, for the Windows session)

After the interrupted upload the partial file was removed, yet the brick's free space stayed at
916 kB of 6000 (it is 4600 kB with no test file). The same happened once before: a `BEGIN_DOWNLOAD`
of 4 MB whose reply was lost (the stale-packet failure, item 4) left the brick with 496 kB free and
no file visible; a power cycle of the brick brought it back to 4600 kB.

Confirmed twice since: after the interrupted upload of the cable pull, a power cycle brought AAA
from 916 kB back to 4600 kB free.

Hypothesis: the firmware keeps the download's file handle open when the transfer stops without a
close — a lost reply or a pulled cable — and the space of the file stays allocated, even after the
file is removed, until the brick restarts. The cockpit cannot close a handle whose `BEGIN_DOWNLOAD`
reply never arrived, but it does know the handle of a transfer cut off mid-way. Worth checking in
the firmware sources (`c_com.c`, the system-command file handles) whether a handle outlives the
USB session and whether `CLOSE_FILEHANDLE` after reconnect frees it.

## What users on Linux will have to do

- **USB: install the udev rule once** (`native/linux/70-lego-ev3.rules`, copy to `/etc/udev/rules.d/`,
  `sudo udevadm control --reload`, re-plug the brick). An extension cannot write `/etc/udev`, and
  `sudo` needs a terminal. Without it the connect now fails with a message that says so.
- **Bluetooth:** nothing measured so far needs setup (the BlueZ D-Bus policy lets a desktop user
  pair and connect on Debian / Raspberry Pi OS); some distributions restrict BlueZ to a `bluetooth`
  group — to check during the Bluetooth backend.
- **TCP and the mock:** nothing.
- **VS Code as Snap or Flatpak:** the sandbox may block USB and Bluetooth; to be documented.
- **SD card in the brick:** RPi OS mounts it as a drive; pulling the cable gives a desktop warning
  that is about that drive, not about the cockpit.

These belong to IMPLEMENTATION_PLAN 0.2.5 (packaging), which the Windows session owns.
