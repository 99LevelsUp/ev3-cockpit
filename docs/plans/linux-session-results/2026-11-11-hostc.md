**Verdict: fails on `f1cfbbf` / `7c1d5a9`; holds on the re-runs at `5488a11` and `dd34e41`.** Compile, lint and
host tests held throughout; 47 unit tests did not run to the end on Linux until the fix in
`scripts/test-setup.cjs` (a referenced interval per test-file process, released by a root `after`
hook). The re-run was done in a separate worktree, Node v20.19.2.

Evidence. Every cancelled test reports `failureType: 'cancelledByParent'`, `error: 'Promise
resolution is still pending but the event loop has already resolved'`. The cancelled suites, all in
five files:

| File | Suites |
|---|---|
| `btPresence.test` | BtPresenceMonitor — paired bricks / inquiry / forgetting a brick (step-3 plan, U3) / a pairing the cockpit made (step-3 plan, KTD11); BtTransportProvider — discovery with presence; BtConnectionQueue — hold-only slots |
| `btWinsockAdapter.test` | BtWinsockAdapter — exchanges |
| `fileTransfer.test` | FileTransferService — writes / reads |
| `transportInfra.test` | BtConnectionQueue; PendingReply utilities |
| `transportTimeouts.test` | BtSppAdapter open deadline |

Cause (diagnosed, not fixed). The code under test arms its timers with `unref()` (13 source files
do, e.g. `btSppAdapter.ts` open deadline, `pendingReply.ts`). When a test awaits only such a timer,
nothing keeps Node's event loop alive, the test-file process drains and `node:test` cancels the
pending test. Example: `BtSppAdapter open deadline › gives up on a port that never opens` is
cancelled after 6 ms instead of timing out at 60 ms. With one extra referenced 10 s timer preloaded
(`--require` of a file containing `setTimeout(() => {}, 10000);`) the same files run clean:
`transportTimeouts` 7/7, `fileTransfer` 8/8. Why the loop stays alive on Windows is not known here.

Host tests: "extension is installed", "activates without throwing", "registers the Cockpit output
channel", "returns the public API, versioned, safe by default", "filesystem commands are registered
and declared" — all pass. During activation VS Code logged once "Extension host … is unresponsive"
and a moment later "… is responsive" (RPi 5 speed; not a failure).

## L6 — an RFCOMM socket to AAA

Packet from the repo's encoder on `7c1d5a9`: `buildCommand({kind:'info'})` →
`21000100004800d30d106081031070810908e120810a08e128810c0ce130810b0ce13c`. Python 3.13 standard

Rule: the socket opens on channel 1 and the brick answers with its name.

**Verdict: holds.**

| Measure | Values |

| Pause after `close()` | Second `connect()` |
|---|---|
| 0 s | `OSError` errno 16 `EBUSY` (Device or resource busy), immediately |

So on Linux, too, a reconnect needs a cooldown of about 2.5 s after close; before that the kernel
first reports the channel busy, then the brick refuses.

### koffi and `socket(31, 1, 3)` from Node

`koffi.load('libc.so.6')`, `int socket(int,int,int)`, `socket(31 /*AF_BLUETOOTH*/, 1
/*SOCK_STREAM*/, 3 /*BTPROTO_RFCOMM*/)` → **a descriptor (20)**, errno 0; `close(fd)` → 0. Load and
call took under 1 ms. So koffi on arm64 can open the Bluetooth socket inside the extension host's
Node, without a helper process.

## Findings

1. **Unit tests cancelled on Linux (fixed in `5488a11`).** 47 tests in five files awaited only
   timers the code arms with `unref()`, so on Linux the test-file process drained and `node:test`
   cancelled them. The test preload now keeps each test file's process alive until its root
   `after` hook; 925/925 and 926/926 pass on HOSTC.
2. **The BT device cache warning repeated every 3 s on Linux (fixed in `dd34e41`).** It now
   appears once; the BT transport and presence lines no longer claim Windows backends on Linux.
3. **Picker warning still Windows-worded.** Opening "Connect a Brick" on Linux logs "Bluetooth
   presence unavailable, the list shows Windows' records only" once. The reason is right, the
   words "Windows' records" are not.
4. **A mixed LE + BR/EDR scan can miss a visible brick.** `bluetoothctl scan on` with the default
   filter did not see AAA in 40 s; a BR/EDR-only scan found all three bricks in about 7 s. The
   Linux backend should scan BR/EDR only.
5. **An unanswered pairing dialog ends after 60 s with `AuthenticationRejected`.** HOSTC gets no
   agent prompt until the owner confirms on the brick, then BlueZ asks for the PIN (legacy PIN
   `1234`, though `LegacyPairing: no` is reported afterwards). If nobody confirms, the brick's
   dialog stays open after BlueZ gives up.
6. **Reconnect cooldown ≈ 2.5 s on Linux as well.** Right after `close()` the kernel answers
   `EBUSY`; for the next ~2 s the brick refuses (`ECONNREFUSED`); from 2.5 s on it connects. Same on
   all three bricks and on both firmware versions.
7. **koffi can open an RFCOMM socket from Node on arm64.** `socket(31, 1, 3)` through koffi
   returns a descriptor; together with the prebuilt `@koromix/koffi-linux-arm64` this means the
   Linux Bluetooth backend (IMPLEMENTATION_PLAN 1.11.11) can live in the extension, no helper.
8. **All four native modules come prebuilt for linux-arm64.** `usb`, `node-hid`,
   `@serialport/bindings-cpp` and `koffi` installed without compiling and load; `libudev-dev` and
   a compiler were not needed.
9. **CCC runs firmware V1.09H**, AAA and BBB V1.10E. Nothing in this session differed because of it.
